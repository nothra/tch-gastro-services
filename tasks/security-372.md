## Geprüft
- [x] **Rollen-Guard vor jedem Schreibzugriff:** `deleteVeranstaltungAction` → `requireRole("veranstalter")` als erste Anweisung (`actions.ts:282`); `setAuslageStatusAction` (`actions.ts:746`) und `removeAuslageAction` (`actions.ts:767`) rufen `requireRole("veranstalter")` vor `offeneAuslageAus` bzw. vor jedem DB-Zugriff auf; `setTeilnehmerActiveAction` → `requireRole("verwalter")` vor dem UPDATE (`app/verwaltung/teilnehmer/actions.ts`, erste Zeile der Funktion). Die neue Hilfsfunktion `offeneAuslageAus` ist kein Export (Modul-intern, keine Server Action) und wird nur nach dem Guard aufgerufen.
- [x] **Zod an der Grenze:** `auslageStatusSchema` (`app/veranstaltung/schema.ts:113-115`, `z.enum` über die DB-Enum-Werte) wird in `setAuslageStatusAction` weiterhin vor dem Schreiben geprüft; die Ablehnung gibt jetzt nur die Custom-Message „Ungültiger Status." zurück (`firstIssueMessage`). Die Ids bleiben, wie vor dem PR, rohe `String(formData.get(...))` ohne UUID-Schema – unverändertes Bestandsmuster, keine Verschlechterung.
- [x] **IDOR (Parent-Key im WHERE):** `setAuslageStatus` und `removeAuslage` filtern auf `auslage.id` **und** `auslage.veranstaltungId` (`db/auslage.ts:103`, `db/auslage.ts:115`). Zusätzlich verlangt `offeneAuslageAus` eine existierende, offene Veranstaltung. `setTeilnehmerActive` (`db/teilnehmer.ts:71-81`) betrifft eine Stammdaten-Entität ohne Parent, die Verwalter-Rolle ist die Grenze.
- [x] **Guarded Write `undefined` ausgewertet (Kern-Kurzregel 1):** `setAuslageStatusAction` → `if (!updated) return { error: AUSLAGE_NOT_FOUND }`; `removeAuslageAction` → `if (!removed) ...`; `setTeilnehmerActiveAction` → `if (!updated) return { error: TEILNEHMER_NOT_FOUND }`; `deleteVeranstaltungAction` → `if (!removed) return { error: NOT_OFFEN }` (`actions.ts:304-305`). Der PR schließt damit die frühere „stiller Erfolg bei No-Match"-Lücke der beiden `void`-Actions.
- [x] **Soft-Delete-Prüfung:** Keine geänderte Action schreibt auf eine soft-deletable Referenz. `setTeilnehmerActiveAction` setzt `active` selbst, eine Prüfung davor ist dort nicht sinnvoll.
- [x] **Lösch-Sperre serverseitig:** `deleteVeranstaltungAction` lädt Zeilen, Positionen und Auslagen zum Zeitpunkt der Action und lehnt bei der ersten Sperre ab (`actions.ts:294-299`); vorher laufen Existenz-, Typ- und Statusprüfung (`assertVeranstaltungAenderbar`, `actions.ts:138-144`). Die Client-Prop `sperren` (`app/veranstaltung/[id]/page.tsx`, `VeranstaltungLoeschen.tsx`) blendet nur die Bestätigung aus. Ein manipulierter Client, der die Action trotzdem aufruft, scheitert am Server-Gate. Die Regel ist eine einzige reine Funktion (`app/veranstaltung/loeschSperren.ts`) für Hinweis und Gate.
- [x] **Kein Open Redirect:** Das frühere Server-`redirect` ist durch `router.replace(VERANSTALTUNG_LISTE_PATH)` im Client ersetzt (`VeranstaltungLoeschen.tsx`). Das Ziel ist eine Konstante (`app/veranstaltung/pfade.ts:3`), nichts davon kommt aus Nutzereingaben.
- [x] **Keine internen Fehlerdetails:** Alle neuen Rückgaben sind feste deutsche Meldungskonstanten (`AUSLAGE_NOT_FOUND`, `NOT_FOUND`, `NOT_OFFEN`, `NO_TEILNEHMER`, `TEILNEHMER_NOT_FOUND`, `loeschSperreMeldung` mit festem `SPERRGRUND`-Record) oder Zod-Custom-Messages. Es werden keine `error.message` und keine Stacks durchgereicht. Die an den Client gegebenen `sperren` sind nur Enum-Literale (`"verzehr" | "kassiert" | "auslage"`) und tragen keine Beträge oder Namen.
